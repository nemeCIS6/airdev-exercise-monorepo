# Convex Backend Handoff — Expense Tracker

_Self-contained handoff for the Claude Code session that builds the Convex backend. Paste this into the session along with `expense-tracker-spec.md`. Frontend is out of scope here — that comes from the Claude Design prototype later._

---

## What this doc is for

This is the **backend-only** build plan. It defines exactly what Convex code Claude Code should write before any UI is touched. Once this is done, the prototype handoff will wire the frontend on top of these functions.

The spec (`expense-tracker-spec.md`) is the source of truth. This doc points to the right sections and adds the things the spec doesn't cover (workspace layout, env setup steps, acceptance checks, the Gemini OCR feature that's deferred to the end).

**Locked decisions** are in `expense-tracker-spec.md` section 0. Do not re-litigate.

## Build order (backend only)

Do these in order. Each step is verifiable before moving on.

### 1. Scaffold

From `apps/web/`:

```bash
npm install convex @convex-dev/auth @auth/core
npx convex dev          # creates Convex project, writes CONVEX_DEPLOYMENT + NEXT_PUBLIC_CONVEX_URL to .env.local
```

Keep `npx convex dev` running in a separate terminal — it watches `convex/` and pushes on save.

### 2. Convex Auth keys

```bash
npx @convex-dev/auth         # generates JWT_PRIVATE_KEY and JWKS, writes to .env.local
```

Then create `convex/auth.config.ts` per the Convex Auth docs (https://labs.convex.dev/auth/setup) and `convex/http.ts` with the standard auth HTTP routes.

### 3. Schema

Copy spec §1 verbatim into `convex/schema.ts`. Save, watch `npx convex dev` push, verify all four tables show up in the Convex dashboard:

- `userProfiles` (with `by_userId`, `by_managerId`, `by_role` indexes)
- `expenses` (with `by_employee`, `by_status`, `by_employee_and_status` indexes)
- `expense_lines` (with `by_expense`, `by_expense_and_sortOrder` indexes)
- `expense_events` (with `by_expense`, `by_expense_and_timestamp` indexes)

Plus the auth tables spread in from `authTables`.

### 4. Auth wiring (`auth.ts`)

Per spec §2.1. Email/password provider via `@convex-dev/auth/providers/Password`. Standard `convexAuth({ providers: [Password] })` export. The frontend `<SignIn/>` and `<SignUp/>` will call into this later; for now just make sure the server side compiles.

### 5. `users.ts`

Implement all five functions in spec §2.2:

- `getMyProfile` — query, returns profile joined with users.email, or `null`
- `completeOnboarding` — mutation, creates profile, role hardcoded `employee`, auto-assigns first available manager as `managerId` if any
- `listMyTeam` — query, manager-only
- `listAllEmployees` — query, manager-only, joins email + current managerId
- `reassignEmployeeManager` — mutation, manager-only

Every function calls `getAuthUserId(ctx)` first. Throw if unauthenticated. Throw if role doesn't match (use spec §2.3's authorization helpers — copy them into a `convex/lib/auth.ts` so `expenses.ts` and `users.ts` can share).

### 6. `expenses.ts`

Implement all thirteen functions in spec §2.3:

Reads: `listMyExpenses`, `listExpensesForReview` (role-aware: manager sees direct reports' `pending_manager`; finance sees all `pending_finance`), `getExpense`

Lifecycle mutations: `createDraft`, `updateDraft`, `saveDraftWithLines`, `submitExpense`, `withdrawExpense`, `resubmitRejected`, `discardDraft`

Approval mutations: `managerApprove`, `managerReject`, `financeApprove`, `financeReject`

Critical rules (from spec):
- `saveDraftWithLines` diffs lines server-side and writes one event per added/edited/removed line, all sharing one `crypto.randomUUID()` `saveGroupId`
- Status is authoritative — manager mutations check `status === "pending_manager"`; finance mutations check `status === "pending_finance"`
- `submittedAt` is set once on first submit and survives withdraw/resubmit cycles
- `withdrawExpense` from `pending_finance` clears `managerDecidedAt` and `managerDecidedBy` (the prior approval is being undone)
- `resubmitRejected` always restarts at `pending_manager`, even if finance was the rejecter. Clears `rejectionReason`, `rejectedByRole`, both decision timestamps, and decision-by fields
- `discardDraft` cascades: delete lines, delete events, delete receipt from `_storage`
- Reject reasons: 5–500 chars, required. Approve notes: optional
- Every event captures `actorRoleAtTime` at write time

### 7. `events.ts` + `files.ts`

`events.ts`:
- `listEventsForExpense` — query, same authorization as `getExpense`, returns events DESC by timestamp, joined with actor displayName

`files.ts`:
- `generateUploadUrl` — mutation, employee-only, returns Convex upload URL
- `getReceiptUrl` — query, same authorization as `getExpense`, signed URL for the storageId

Server-side validation of receipt file: in `updateDraft`/`submitExpense`, call `ctx.storage.getMetadata(receiptStorageId)` and reject if MIME isn't `image/jpeg | image/png | image/webp | application/pdf` or size > 10MB. Do not trust the client.

### 8. `seed.ts`

Per spec §5. Idempotent — check by email before inserting users. Place placeholder receipt JPGs in `convex/seed-assets/` and upload each via `ctx.storage.store()`.

Three users:
- `employee@example.com` / `employee123!` — Eddie Employee, role `employee`, `managerId` → Morgan
- `manager@example.com` / `manager123!` — Morgan Manager, role `manager`
- `finance@example.com` / `finance123!` — Fiona Finance, role `finance`

Five expenses on Eddie (one per status):
1. Draft — Office supplies, 2 lines, no receipt
2. Pending Manager — Bistro 12 lunch, 3 meal lines + receipt
3. Pending Finance — SaaS subs, 3 software lines + receipt + Morgan approval
4. Approved — SF conference, 2 lines + receipt + both approvals
5. Rejected — Team offsite, 1 vague line + receipt + Morgan rejection (reason: "Please itemize…")

Each `line_added` event in the seed shares one `saveGroupId` per expense so the history collapse works.

Run via `npx convex run seed:run`.

### 9. Acceptance checks (before declaring backend done)

Open the Convex dashboard and verify:

- [ ] All four app tables exist with the right indexes
- [ ] Auth tables exist (`users`, `authSessions`, `authAccounts`, etc.)
- [ ] `npx convex run seed:run` creates exactly 3 users, 5 expenses, 11 line items, 17 events on first run
- [ ] Re-running seed creates **zero** new records (idempotency)
- [ ] Manually log in (via a throwaway sign-in form or the Convex dashboard) as each test user:
  - Eddie sees his 5 expenses via `listMyExpenses`
  - Morgan sees the 1 `pending_manager` expense via `listExpensesForReview`
  - Fiona sees the 1 `pending_finance` expense via `listExpensesForReview`
- [ ] `getExpense` enforces authorization (employee can't read another employee's expense; manager can't read non-direct-report's expense; finance can read any)
- [ ] `managerApprove` on the seed's pending_manager expense advances status → `pending_finance` and writes a `manager_approved` event with `actorRoleAtTime = "manager"`
- [ ] `financeReject` on the pending_finance expense (after manager approval) transitions to `rejected` with `rejectedByRole = "finance"`
- [ ] `withdrawExpense` from `pending_finance` clears `managerDecidedAt` / `managerDecidedBy`
- [ ] `resubmitRejected` on the rejected seed expense lands at `pending_manager` and clears all decision fields
- [ ] Receipt upload roundtrip: `generateUploadUrl` → upload a JPG → `getReceiptUrl` returns a working signed URL

## §8. Gemini OCR — receipt auto-populate (LAST feature, do NOT build until everything above is done and the frontend is wired)

**Final feature, added at the very end of the build.** Skip during the main backend pass. Comes back after the form is wired so we can demo it end-to-end.

### Goal

After an employee uploads a receipt to a draft expense, surface an "Auto-fill from receipt" button. Clicking it calls a Convex action that sends the receipt to Gemini Vision and returns a structured list of line items. The form prefills those lines; the employee can then edit/save/submit as normal.

### Where it lives

New file: `convex/ai.ts`. It's an **action** (not a query or mutation) because it does external HTTP to Gemini.

```typescript
"use node";
import { action } from "./_generated/server";
import { v } from "convex/values";
// import the Gemini SDK or call the REST API with fetch

export const extractLinesFromReceipt = action({
  args: { storageId: v.id("_storage") },
  handler: async (ctx, { storageId }) => {
    // 1. Auth check — must be the employee who owns a draft pointing at this storageId
    //    (look up via expenses table; if no draft references this storageId for the caller, throw)
    // 2. Fetch the file blob from Convex storage:
    //    const blob = await ctx.storage.get(storageId);
    // 3. Call Gemini with the blob + a structured prompt (see below).
    // 4. Parse the response into ExtractedLine[] and return.
    //    Do NOT write to the DB here — return data; the client decides what to insert.
  },
});
```

### Prompt to Gemini (use `gemini-2.0-flash` or `gemini-1.5-flash` — multimodal, cheap, fast)

System / instruction:

> You are extracting line items from a receipt image (or PDF). Return ONLY a JSON array of objects with this exact shape: `{ "description": string, "category": "travel"|"meals"|"lodging"|"software"|"supplies"|"other", "quantity": number, "unitAmount": number }`. `unitAmount` is per-unit in the receipt's currency (a number, no symbol). If a line shows a total only, infer quantity 1. Tax, tip, service charge, and gratuity each become their own line with category "other" (or "meals" for tip on a meal). Skip subtotals and grand totals — those are derived from the lines. If the receipt is unreadable or has no line items, return `[]`. Do not include any text outside the JSON array.

Pass the receipt blob as the multimodal image part. Request `responseMimeType: "application/json"` to force JSON output (Gemini supports this).

### Auth + validation

- Action must verify the caller owns a draft expense whose `receiptStorageId === storageId`. Throw otherwise.
- Validate the parsed JSON before returning: each item has all four fields, `category` is in the enum, `quantity > 0`, `unitAmount > 0`. Drop malformed items rather than throwing — partial extraction is better than none.
- Cap result to 20 lines (defensive).

### Env var

`GEMINI_API_KEY` — set locally and in Convex production via `npx convex env set GEMINI_API_KEY …`. Reference in the action via `process.env.GEMINI_API_KEY`. Throw a clear error if unset.

### Client wiring (frontend touches it, but worth noting)

The "Auto-fill from receipt" button in the new-expense form calls the action via `useAction(api.ai.extractLinesFromReceipt)`, receives the array, and inserts them into the line-items section as unsaved rows. The employee then clicks Save Draft (which fires `saveDraftWithLines` and writes the `line_added` events).

### Failure UX

- No receipt uploaded yet → button disabled with tooltip "Upload a receipt first."
- Gemini returns `[]` → toast "Couldn't read any line items. Enter them manually."
- Gemini throws / times out → toast "Receipt OCR failed. Enter line items manually." Don't block submission.

### Acceptance for §8

- [ ] `GEMINI_API_KEY` set in Convex env
- [ ] Action throws if caller doesn't own a draft for that storageId
- [ ] Uploading the seed's "Bistro 12" receipt JPG and clicking Auto-fill returns 3-ish reasonable line items
- [ ] Malformed Gemini output doesn't crash the action — returns `[]` or partial valid items
- [ ] Action does NOT write to the DB — pure read/transform
